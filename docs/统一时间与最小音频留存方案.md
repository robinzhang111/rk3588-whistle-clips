# 统一UTC时间与最小音频留存方案

2026-10-14当前实施顺序见[核心功能闭环规划](./核心功能闭环规划.md)：已有分块文件/相对片段链路不重做，先本地持续输入源与生命周期模拟，再现场采集和真实采样UTC。默认不保存连续音频不变。没有实际采样锚点时仍为相对候选；合成锚点只可作软件测试，不能转成真实UTC验收。当前本次仅规划，未改变运行配置或启动硬件。

更新日期：2026-10-13。用户确认的产品默认方案；已有分块WAV接口及电脑/板端NPU文件模拟验证，真实持续采集、采样UTC、录像时间映射及端到端片段定位尚未验收。

## 1. 默认运行流程

板端麦克风持续采集 → CPU短时内存缓冲/重采样/分窗/FFT → 已验证FP16 RKNN的NPU前向 → CPU执行0.65/v1、估计哨声UTC起点 → 本地持久化事件标签并上传电脑。正常运行不落盘原始音频、不上传整场录音，处理过的音频在满足重叠窗和事件处理需要后释放。缓存保持有界，不随着比赛时长增长。

录像设备拍摄 → 赛后文件导入或后续实时传输到电脑 → 电脑建立录像媒体位置与UTC的映射 → 按哨声标签定位 → 保存前后片段。录像传输和标签传输可以独立进行，赛后导入可以先做，不必同时升级实时视频。

两路音轨拍手匹配是可选调试/备用校准方式，不要求正常运行保存板端音轨。默认路线不要求录像必须带音轨，但已有录像音轨可以用于人工复盘与按需纠错。

## 2. 三种时间关系

- 标准时间：两端墙钟采用UTC，记录同步来源、核查时刻及偏差/漂移依据。显示日期正确或一次校时不等于持续精确同步。
- 板端采样时间：记录实际采样位置与单调时钟/UTC的锚点和误差，按哨声估计起点对应的样本位置换算时间。命令启动、模型返回和标签到达电脑时刻都不能替代。
- 录像时间：记录视频某个媒体位置/帧对应的实际采集UTC、依据与误差，检查时间码/采集时间戳、录制延迟、分段和导出/拼接影响。操作开始时刻、文件创建时间、电脑收到视频的时刻不默认等于帧的拍摄UTC。

“录像机和板卡按同一标准时刻开始”可以用于组织会话，但启动命令同步不证明采集起点相同；最终必须核对实际时间映射。若相机没有可靠的拍摄UTC，需要一次有依据的可观察校准，或选择能提供可验证采集时间的录像链路。相机准确型号及上述能力仍待核实，不假设已有时间码或同步接口。

连续且无中断区间的初步映射为：

```text
板端事件UTC Te = 已核验采样锚点UTC Ta + (事件原采样位置 ne - 锚点位置 na) / 原采样率 fs
录像位置 Ve = 已核验录像锚点位置 V0 + (Te - 锚点采集UTC T0) × 时间比例 a
```

初始a=1只适用于已核对的时间比例。采样时钟漂移、重采样、丢样、时间跳变或录像分段中断出现时，需保留位置转换依据、重新锚定或分段映射，不能用一个错误起点覆盖整场。进程计时用单调时钟，墙钟校准不应无记录地改变既有事件时间轴。声音传播/拾音距离也影响声音到达时刻，最终定位误差一并实测。

## 3. 标签与映射记录

沿用现有session_id、event_id、event_type、event_time_utc四字段JSONL/HTTP接口，不在本次设计更新中改通信合同。event_time_utc代表估计的声音发生时刻；先本地保存再发送，电脑保存确认不等于片段已生成。

采样位置、算法确认时间、同步状态、偏差依据、缺失区间及模型版本等必要诊断信息可随会话单独记录，不要求附原始音频。无可信UTC锚点时保留相对时间候选和待定位状态，不编造UTC或以接收时刻生成正式发生时间标签。电脑无可靠录像映射时可以接收标签，但片段保持待对齐，不输出定位成功结论。

阶段一现有align/extract可表达手工建立的锚点和比例；锚点改为经核验的UTC—录像位置，不依赖拍手这一特定来源。自动读取相机时间信息/建立映射尚未实现，历史模拟对齐也不是这条默认方案的实测证据。

## 4. 音频留存与资源

| 使用场景 | 音频策略 | 保存内容 |
|---|---|---|
| 正常比赛检测（默认） | 仅有界短时内存缓存，处理后释放；不落盘/上传连续原始音频 | 事件标签、必要版本/时间映射/状态日志 |
| 麦克风有效输入验收 | 明确开启一次短时受控录音，完成格式/哈希/听辨后单独归档 | 本次诊断原件及结果，保留历史文件 |
| 误报/漏检排查、时间校准 | 按需明确开启少量调试片段或同步录音 | 独立调试文件，记录用途，不自动变成全场留存 |
| 已有文件推理与纠错测试 | 继续使用既有WAV/录像及已保存输出 | 保留原件/参考/纠错，不能为新策略删除旧材料 |

分块WAV正常模式已实现只写相对候选/汇总/必要日志，不新建连续WAV、特征或逐窗分数；显式对照诊断另存分数，见[分块接口验收](../阶段2_离线哨声检测/分块WAV持续接口操作与验收.md)。这不证明真实麦克风无落盘采集或整机长期内存稳定，实际采集接入时调试录音仍默认关闭并单独核对。无可信采样UTC时，文件模拟不生成或上传正式UTC标签。

减少原始音频写入和网络传输可以减少相应I/O与流量，但CPU采集/预处理和NPU前向仍持续运行；整机功耗是否降低及幅度待测。若报告节能，使用相同输入/运行负载对比留存开启/关闭的存储、流量与功耗，不把设计理由当实测收益。

## 5. 实施顺序与验收

1. 板端：沿用已验证模型，把必要NPU推理接口接持续麦克风采集、有界缓存和事件处理；有效声音、缓冲/重叠窗口、持续处理与丢样分别验收。短时录音可以用于有效输入验收，不要求产品保存整场音频。已有多声道/较长文件测试可按需要补，通用文件工具完善不作为麦克风接入前置。
2. 时间：核查两端时间源、偏差和漂移，建立采样锚点UTC；掉线、采样中断或时钟跳变有记录。未验证的状态不发布可信UTC事件。
3. 通信：复用已验收事件上传接口，另验自动哨声标签和板端/电脑逐字段一致、重复/延迟发送处理。
4. 录像：确认型号及可靠时间信息，建立实际拍摄UTC—媒体位置映射；用独立可观察事件验证起点/中段/结束误差与分段行为，再自动截取。
5. 默认不落盘模式与调试留存分开检查；正常运行仅事件/必要日志写入，缓存有界；功耗收益另测。

未预设毫秒级精度和功耗下降比例。端到端定位目标需按片段用途约定，报告采样定位、时钟、录像映射、声传播和截取误差的实际影响。NPU单文件通过、通信通过、录音通过分别只是子任务，阶段二/三及完整系统不能据此自动宣布完成。
