更新日期：2026-10-12。当前以先完成可用工程为主：已有模型先接完整使用流程，使用中收集人工纠错，之后按版本改进模型。原有数据核查、分组与评价材料保留，服务后续改进，不作为启动原型的门槛。

2026-10-13更新：电脑统一检测/纠错和04B CPU/NPU单文件对照已限定验收。用户确定后续板端默认NPU模型推理，CPU负责采集/预处理和事件/保存/上传；CPU原H5保留按需对照。当前正式采集链路仍待实现和验收，下面电脑原型要求保留为已完成子任务合同。

2026-10-13时间/留存决定：正常板端仅短时内存检测，保存上传UTC标签，不保存/上传整场录音。录像由电脑按实际采集UTC映射定位；两路音轨仅调试/备用。现有单文件部署已限定验收，接下来优先有效拾音/持续采集/采样UTC与自动标签，文件覆盖按需补。见[统一时间与最小音频留存](./统一时间与最小音频留存方案.md)。

## 当前状态与依据

- REC 手动事件与标签通信子任务已验收；阶段三实时视频、自动哨声通信集成尚未验收。
- 电脑独立 CPU 环境已实际加载 NaoDevils WhistleNetMk16；连续录音、篮球输入适配、分数和 v1 事件输出已有运行证据。见[电脑模型运行](../阶段2_离线哨声检测/电脑端模型推理操作与验证.md)、[篮球输入适配](../阶段2_离线哨声检测/篮球音轨输入适配验证.md)与[篮球固定模型验证](../阶段2_离线哨声检测/六场篮球片段固定模型验证.md)。
- 当前复用原模型、阈值0.65及v1规则，不以训练、换模型或先优化规则代替完整流程实现。v2A 曾误合并独立吹哨，保留为诊断，不替换默认v1。
- [篮球失败核查](../阶段2_离线哨声检测/篮球检测失败核查结论.md)确认鞋声、喊叫误响应，短哨过滤和两声未分离，以及事件末端拖长。第一版是需要人工核对的原型，不称可靠自动裁判标注系统。
- 现有15个篮球来源共27条历史人工参考事件及用途分组提案已整理，见[数据统计与用途分组](../阶段2_离线哨声检测/现有数据统计与用途分组方案.md)。B01最新两声纠错与旧一声参考分别保留，不重算历史汇总；分组提案不等于冻结训练集，不以样本数量/分组作为原型前提。RK3588单文件CPU/NPU兼容及计时已限定验收，板载有效录音、持续速度/丢样和UTC采样映射待验收。

## 1. 电脑完整检测与标注原型：阶段二，聊天04，已限定验收

使用链路：**篮球视频或WAV → 音频解码与输入适配 → 固定模型分数 → v1独立事件 → 保存候选标注与运行记录**。

- 使用现有 Python＋FFmpeg 和独立推理环境，复用已有适配/推理/事件工具，不复制一套新算法。支持用户指定文件，而非只能运行固定实验清单。
- 视频按音轨解码；WAV直接读取。自动处理实际采样率和声道，沿用现有22050 Hz、1024点Hamming窗、512步长、513频点20log10幅值特征合同与静音有限性处理。记录原始格式、转换和位置映射，不改输入原件。没有音轨的输入明确提示。
- 固定原H5权重、阈值0.65、任一路阳性且连续至少2窗、无桥接的v1事件规则。保留现有完整窗/EOF约定和尾部范围记录；不启用v2A、不在本轮调阈值。
- 保存事件起止相对秒数、事件ID、对应分数及其汇总定义、模型/阈值/规则版本、输入来源与运行日志。模型分数不称经过校准的真实概率。
- 无可信录音UTC起点时只保存文件内相对时间；视频媒体时间映射需记录音轨起点和偏移，不用文件创建时间冒充采集时间。后续板端UTC事件与当前本地候选标注是不同接口。

工程验收：选现有WAV和带音轨篮球视频分别跑通，核对采样率/声道适配、事件文件可读、起止在有效输入范围内、位置映射和重复运行结果。播放若干候选核对定位，明确保留已知误报/漏报。首次版本目标是流程可使用，不要求检测准确率达到预设值；软件流程通过与检测质量达标分开报告。持续录音、自动截取比赛画面和现场执裁均不属于本步验收。

## 2. 人工纠错入口：阶段二，聊天04

在模型候选基础上支持删除误报、补充漏报、修正起止和另存反馈。复用现有播放/波形/标记材料能力，避免再要求用户从零标完整数据才能使用。

保留原预测不可覆盖；另存原事件引用、纠错操作、修正边界和人工确认状态。导入纠错后可恢复查看，校验边界及来源匹配。人工确认的声音类别与裁判身份分开记录，未知身份不自动标成本场裁判。

验收：实际完成删、补、改各一例并重新导入核对，原预测和旧人工标注保持。反馈可逐步积累为训练材料；模型自预测、未核查背景和未确认候选不自动成为正确训练标签。

## 3. RK3588实际接入：阶段二，复用阶段三通信

后续板端正式模型推理默认NPU，采用已验证FP16 RKNN；CPU负责采集/缓存、重采样、分窗、FFT、0.65/v1事件及存储通信，原H5 CPU仅按需对照排查。已有一份文件CPU/NPU行为和计时限定验收，见[部署验收](../阶段2_离线哨声检测/RK3588文件推理部署与对照验收.md)。优先把必要NPU接口接有效麦克风、持续输入和有界短时缓存，文件覆盖按需要补。正常模式音频处理后释放，仅标签与必要日志保存上传；短时受控录音及哈希/幅值/听辨属于独立调试验收，再评估持续速度、丢样和漂移。当前文件工具不等于在线链路已实现，电脑通过不替代板端实测。

依据采样位置生成独立事件，区分哨声估计起点、算法确认时刻和电脑接收时刻。只有UTC映射有依据时才沿用现有 session_id、event_id、event_type、event_time_utc 四字段，先板端保存，再接阶段三HTTP/SQLite/label_saved链路；相对秒数、结束时间和分数保留在检测输出中，不直接塞入旧通信协议。

验收分别记录有效拾音、同文件兼容性/输出一致性、板端速度、实际声音效果、事件上传和时间关系。已有REC通信不能代替自动哨声集成验收。真实录像跨设备同步和实时视频继续后置；读取视频音轨是当前电脑输入能力，不代表录像链路已完成。

## 4. 定期模型更新：阶段四，聊天05

采用“固定版本使用 → 人工纠错积累 → 本地训练/验证候选 → 另存新版本 → 验证部署并替换 → 可回退”的批次流程。运行中的模型不边检测边更新权重。

训练时再按录音/比赛来源划分数据，避免纠错片段和同源声道跨集合；已有分组与评价材料继续复用。用人工确认标签，不把模型预测直接当正确答案。对比固定现用版本和候选的漏检、误触发、起止质量、耗时与资源，报告数据规模和用途限制。

版本记录绑定原权重、ONNX/RKNN派生模型、输入预处理、阈值与事件规则；候选不覆盖现用或历史模型。后续部署默认NPU，新版本本地验证及转换/数值检查后再上传RK3588实测，保留上一NPU版本、原H5 CPU参考和回退方法。具体微调或小CNN结构按反馈决定；不兼容候选先保留现用NPU版本，不用未经验证的转换替换。训练与性能结论必须有相应证据，本轮不开始训练或替换模型。

## 5. 已有研究材料的用途

B-Human原件、派生标注、传统v1失败、TestBench复评、篮球人工纠错与历史输出全部保留。传统方法成为对照和失败分析依据，不要求先把传统v2改到合格才复用现有模型。数据来源、许可、分组与评价约定在训练/公开发布相应材料时仍按需核查；无需为原型先补齐所有材料或达到固定数量。
