# 篮球正负样本与最小模型改进准备方案

日期：2026-10-12。状态：证据整理与方案，不是已生成训练集或已开始训练。用户新素材以几秒至几十秒短片段为主。本轮不训练、不调0.65阈值、不跑新推理、不上传板卡、不集成通信。

## 结论与推荐路线

先做哨声／非哨声二分类，将鞋底摩擦、喊叫、计时器和其他背景作为负样本的来源标签；不要求模型先输出三种声音类别。推荐补充独立来源数据后，先对现有WhistleNet进行受控微调对照；若分类层适配和小范围解冻都不能降低场景误响应，再比较一个同输入的小CNN。二者都先保留当前前端、0.65阈值和v1事件规则，避免同时改前端、权重与事件规则而无法定位效果。

这是可验证的工程路线，不承诺更高准确率或部署时延。模型是否值得微调、输入是否与训练分布一致、数据是否够用均须按新数据验证。不能用全局合并或取消连续两窗来掩盖分类器对鞋声／喊叫的持续响应。

outputs/basketball-data-plan-20261012-01/sound-evidence.json保存24条有明确来源的索引（7正事件、13非哨声FP区域、4哨声后非哨声区域）。每条绑定原浮点WAV/视频SHA256、比赛分组、原44100Hz样本位置、反馈或真值出处与边界状态。不切新音频，不生成训练窗口。

17条非哨声证据范围按原文件做重叠/相接区间并集，得到13个不重叠范围、合计约6.48553秒，存negative-region-unions.json。这个并集仅防止重复统计，不等于13次独立声音或已经验收的精确训练标签。索引与并集均未与当前7正区间重叠，但人工边界附近仍有不确定性。即使能切成很多重叠窗，独立证据仍仅6场，不能靠增广/复制把它说成大数据。

### 标签合同

- 训练候选主标签：1=可辨认哨声，0=非哨声。鞋声／喊叫／计时器／球声／普通背景保存为subtype，供采样和分组错误报告；不是必须训练的多分类输出。
- 另外保存source_identity（本场裁判／邻场／回放或后加声音／未知）。目前7正来源未知，只能支持声音类型任务。若最终坚持只检测本场裁判，必须有来源依据和可分辨输入条件；单声道中本场/邻场同样哨声未必能靠声音类别分开。不能把未知哨声当邻场负样本或承诺二分类完成场地身份判断。
- 回放、重复播放与现场声音分别记录。不能把同一吹哨的回放当新的独立来源；若工程不要回放触发，需明确额外识别依据，不混入矛盾标签。
- 模糊声音、正负重叠、难区分的回声/混合声音先记录uncertain并复核。不得直接作为阴性。当前FP01具体声型、L04间隔、B04计时器不生成细分类训练真值。
- 单个窗口必须单独满足标签条件。不要把“整个3秒片段里有一声哨声”变成所有窗口都为1，那会同时教模型对喊叫和鞋声持续触发。未标背景也不自动当阴性，需完整听辨。

### 开始生成训练数据前需补

- [ ] 对候选负区域重新按原声音标可靠起止，给哨声末端附近留不确定区；不能直接用模型候选起止作为自然噪声标签。
- [ ] 确认片段里是否有配乐、解说、回放、叠加音效、响铃等，并记录来源和影响。
- [ ] 补充真实哨声变化：短吹、长吹、连吹、音量/距离/场地/哨子差异；不只用清楚的大声哨。
- [ ] 补充困难负样本：鞋底尖锐摩擦、多人喊叫、计时器/蜂鸣、拍手、球弹地、普通说话和安静背景；必须有明确“无哨声”依据。
- [ ] 补充哨声到喊叫／鞋声过渡以及两次独立连吹的完整上下文，不只保存孤立声音，供事件起止/分离评价。
- [ ] 用真实比赛/原始录像分组，确认新文件是否同一场、重复下载、裁剪/重编码/不同声道或同一次回放；同源全部同集合。
- [ ] 明确模型训练数据用途及来源。原data/Robcup发布test不加入训练；其train若作辅助需另核标签/特征合同与来源映射限制，不能认为大量NPY行就是大量独立比赛。
- [ ] 如下一步训练，另建阶段四训练环境与模型版本，先检查旧H5训练兼容，不更改阶段二推理环境或覆盖旧模型。不执行上游带训练/清理副作用的顶层脚本。

### 用户提供短片段时的最小采集建议

不要求现在现场录音。优先给包含动作前后背景的10～30秒原片段，不只截一个哨声中心；鞋声或喊叫片段应确实无哨声，并尽量留其起止。几秒片段可补声音种子，但对背景误触发评价作用有限。保留原文件，不先自行增益归一化或只发重新压缩的音频。

建议作为第一轮工程试验的收集目标，而非充分性或准确率承诺：

|用途|来源建议|声音覆盖建议|
|---|---|---|
|开发/未来训练|现有6场只作种子，另补至少6个新比赛来源|至少30～50次人工确认独立吹哨；分别补30～50段鞋声、喊叫场景；另补普通背景及计时器等|
|验证/方案选择|至少3个未与开发同源的新比赛|10～20次吹哨及明确负片段，覆盖短吹与连吹，不参与训练|
|保留评价|至少3个与前两者不同来源的新比赛|10～20次吹哨及足量纯负片段；冻结模型/规则后才看模型输出|

上述数量是可执行的初始采集建议，不是学习算法保证或硬性放行。资源不足可先少量做功能试验，明确“小样本”，不宣布可部署。同一场很多短片段增加声音覆盖但不会增加独立比赛数。当前负证据13个范围/6.49秒不等于已达到建议负样本量。

## 新比赛片段评价准备

1. 登记每个新文件的路径、源比赛ID、原录音ID、来源描述、时间段/是否回放、文件SHA256；不明同源关系先归为同组或待查，不凭文件名不同判独立。
2. 在任何新模型评分前固定用途。旧6场已参与选择和误响应分析，若用于改进只能作开发/训练诊断，不能后来转成保留测试。
3. 按源比赛整组分开发/验证/保留，声道、相邻切片、增广和转换副本全部继承父集合。增广仅训练集合；不要随机打散重叠窗口做验证。
4. 先人工完整听实际声道，隐藏模型分数，标每次独立吹哨与明确负区间/背景，不确定声收敛后保存真值hash。未来若因模型输出发现标注问题，另存修订并说明重新评价，不静默覆盖。
5. 转换保持已经验证的原float尺度/44100→22050合同；训练/推理前端一致。试听统一降音量的PCM16不得作为默认训练输入。需要新的尺度变换时另定合同并验证，不暗改现有前端。
6. 第一轮保持1024窗/512步长/513 FFT特征。训练窗口必须明确属于可靠正/负区间；边界混合窗先排除，建议预留一hop不确定带作为待验证准备规则；短到不足完整窗的区间保留事件证据，不补零制造可训练窗，也不删除它们在事件评价中的漏检。
7. 负样本包括困难负样本与普通背景，不能全用“模型已经触发的负例”。不要仅按音量区分；记录真实音量/压缩和混合声音，避免正负来自截然不同录制链路。训练窗再多也要按物理来源和会话报告样本量。
8. 评价继续原音轨起点0.2秒、一对一、全部未匹配FP/FN；同时列短吹/连吹、鞋声/喊叫子集、重复触发、末端拖长、分离失败。声音混合场景不能只看二分类窗准确率。
9. 短片段指标至少报告TP/FP/FN、P/R/F1、纯负片段中触发比例（分母仅人工确认整段无哨声片段）、每个片段触发数、实际音频总时长。可列同批短音频FP/小时折算，但明确选择性短片段不能推断完整球场每小时水平，既有70.60秒不外推。
10. 冻结权重/前端/0.65阈值/v1与代码hash后使用保留评价；看过保留输出后不再用它选择方案。若继续改，则这批转开发诊断，另留新来源。

## 最小模型改进与替换对照

|方案|具体边界|主要取舍|当前决定|
|---|---|---|---|
|M0：原模型|原H5、原前端、0.65/v1|已有失败基准，不再调合并参数隐藏问题|始终保留对照|
|M1：复用原模型适配|先冻结特征层，仅适配末端分类层；数据增加且验证支持后再小范围解冻、低学习率微调|实施最小、保留现有接口；原特征可能已把鞋声/喊叫混在一起，只动分类层可能无效；小样本易过拟合|优先候选，尚未训练|
|M2：换小模型|同513×1输入的简洁1D CNN（二个卷积块＋池化/GAP＋二分类输出）作另一个候选|保持前端便于对照；从零学习需要更多独立数据，没有效果/算量/部署承诺|M1不满足时再考虑，尚未实现|

冻结特征、先适配分类层，再考虑低学习率解冻的通用流程参照[Keras官方迁移学习指南](https://keras.io/guides/transfer_learning/)。该指南不证明旧H5在当前版本可训练，也不证明哨声任务会改善；本项目旧H5训练需要单独核查。不能复制指南代码顺便升级推理环境。

第一轮不并行增加多分类、时序网络、log-mel前端、阈值扫描、混合事件规则和RKNN转换。若相同前端的小模型仍无法分开两声，第二轮再论证短时序上下文或其他特征，每次只引入明确变量，并保持新独立评价。M2结构只是候选草案，不生成源码或训练配置。

未来训练方案只在开发/验证来源选择权重与早停，使用二分类损失；具体学习率/轮数/类别采样在数据验收后另定，不现在凭7个事件承诺数字。保留0.65主对照，新权重分数校准不同，不能认为0.65自动是最佳阈值；本轮不调阈值，未来若需要校准须另授权并仅用验证集，不能看保留测试挑阈值。

### 验收判断

- 降低鞋声／喊叫子集误响应，同时不吞掉独立连吹或牺牲短哨召回；更好的窗准确率不能替代事件评价。
- 固定模型与同规则成对评价M0和选定候选，列全部错误与逐比赛结果，不挑最好种子/片段汇报。
- 需要改善持续响应使末端接近人工哨声边界，仍明确人工近似边界和实际采集/UTC误差不同。
- 本场/邻场身份、完整背景小时误触发、RK3588时延/资源和稳定性仍需各自数据与验收。数值工程目标（最低召回、误触发预算、起止/延迟要求）必须在开启保留测试前约定；本轮不替用户承诺通过标准。
